## Reliability update 0.2.1 (build 3)

The watchdog consumes queued acquisition before checking freshness. Synthetic tests cover a one-second UI stall, menu-tracking coalescing, real sensor lag, gaps, source switches, reference jumps, invalid samples, terminal errors, and expired acquisition.

Holding still never recalibrates; only an explicit Set center replaces zero. A fresh return may resume previously active capture using the retained reference. Manual pause, selection changes, and reset cancel that resumption. Detected source, clock, or reference changes invalidate use of the stored reference rather than replacing it silently.

Synthetic sensor tests exercise the real MotionService through injected transport, clock, and attitude boundaries. ## Camera anchor and energy update, 0.7.0 (build 8)

The wearer explicitly rejected build 7's retained-reference behavior: removing AirPods while facing left and reinserting them shifted the apparent screen center, including when reinserting while facing right. Keeping the same saved quaternion and unchanged center revision did not preserve physical heading. This supersedes the pending physical acceptance above. AirPods-only mode now makes a saved reference unusable after missing motion/removal and requires explicit Set center; it does not guess zero from a newly still pose.

Three additional reports investigate independent camera anchoring, per-session AirPods/camera alignment, and energy use: [camera research](../research/CAMERA-ANCHOR-RESEARCH.md), [fusion design](../research/HEADING-FUSION-DESIGN.md), and [energy research](../research/ENERGY-RESEARCH.md). The implemented camera prototype is optional and off by default. Its Enable button is the only camera permission-request entry point. Built-in-camera frames are analyzed locally and discarded. A screen-facing setup plus a short head turn saves camera-space neutral and learns yaw sign. Brief recovery bursts measure the current turned angle against that durable center, rebuilding only the disposable AirPods alignment. A missing/ambiguous face, changed layout, or failed check cannot silently establish a new zero. Physical camera correctness remains unverified.

The energy complaint was independently observed: Activity Monitor showed current Energy Impact 1556.2, while a paused, noncapturing AirVeil process used 36.1% CPU in a snapshot and averaged 53.76% over a subsequent ten-second observation. The profile contained substantial SwiftUI view reconstruction. These observations were not a controlled active-blur comparison; Energy Impact is a relative metric, not watts. The old app was stopped during development to avoid continued load.

The first optimization stage isolates rounded tracking telemetry in small views, sends animation directly to the renderer, pauses a settled animation clock, stops hidden/inactive preview work, and deduplicates menu/window changes. Rendering is demand-driven with bounded/coalesced frame notifications and GPU-busy retry. Clear or fully solid overlays skip source blits and all Gaussian passes; returning to blur consumes the newest retained frame. Native capture size, 60-fps ceiling, and the existing blur-quality bank are unchanged. Live energy savings still require an installed-app comparison.
